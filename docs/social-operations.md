# 助手A 外部チャネル運用

この文書は[集客・コンテンツ導線戦略](../ACQUISITION_STRATEGY.md)の実行手順。X、note、itch.ioは発見の入口、`https://joshu-a.com/products/<slug>/` は製品を理解して次の行動を選ぶ正本とする。実製品・実測・実際の制作過程だけを扱い、投稿数を目標にしない。ゲームの購入・DLなど、その媒体内で完結すべき行動は無理に公式サイトへ迂回させない。

[製品公開手順](product-launch.md)と`node scripts/check-release.mjs`は、購入・DL・利用が可能な正式公開製品のページとCTAを検査する。この文書は外部媒体への投稿判断・原稿・導線を扱い、release gateの代わりにはならない。公開前デモでは未公開を明記し、実在しない製品URLや購入先を作らない。

## 公開前の共通判断

投稿の材料を「1回の製品更新」として記録し、次を確認する。1つでも欠ければ投稿しないか、事実確認できる範囲に縮める。

1. 実際に公開・検証した事実、または明確に「開発中」と示せる実物がある。
2. 読者にとっての変化・使い道を一文で説明できる。数字、対応環境、価格、予定日は根拠を確認した。
3. 公開済み製品の告知なら、製品ページ・主CTA・購入/DL/利用先が実際に開く。公開前デモは未公開を明記し、購入を促さない。
4. 画像・動画・コード片に秘密情報や他者の権利侵害がなく、スマホでも要点が見える。
5. その媒体の読者に価値がある。媒体を埋めるために同じ文面を流用しない。

投稿価値が高いのは、新製品、意味のある大型更新、見た目や操作で分かる改善、ユーザー影響のある修正、根拠を示せる技術的発見・実測、過程自体が参考になる制作記録。投稿価値が低いのは、内部だけの細かなリファクタ、一般論だけのAI活用、進展のない作業報告、検証していない性能主張、内容の薄い連投、記事やストア説明の丸写し。小型更新は利用者に明確な利益があるときだけ投稿する。

投稿頻度はイベント駆動。リリース時と重要更新時に告知し、実物を見せられる週だけXに追加のデモや学びを出す。目安は活動中でも週0〜2件で、ゼロの週があってよい。noteはまとまった背景や検証が書けたとき、itch.ioのdevlogはゲームの公開・重要更新時に限る。毎日投稿を前提にしない。

## X: 短い発見と製品ページへの入口

| カテゴリ | 中身・証拠 | 主な行き先 |
| --- | --- | --- |
| リリース告知 | 何ができるか、誰向けか、実画面 | 該当製品ページ |
| 大型・小型更新 | 変化と利用者の利益、必要ならバージョン | 該当製品ページの更新情報 |
| 短いデモ | 1操作・1結果を短い動画や画像で示す | 公開済みなら該当製品ページ |
| 開発成果・制作過程 | 実装したものと判断理由、途中ならその状態 | 関連製品ページが公開済みのときだけリンク |
| 技術的な学び | 課題、試行、検証結果、限界 | 詳細がある場合は対応するnote記事・製品ページ |
| 不具合修正 | 利用者への影響と直ったこと | 更新情報またはサポート先 |

プロフィール文案（公開製品を装わない）: **「助手A｜ソフトウェアとゲームを個人開発。『使いやすく、少し面白いものを。』制作・検証で得たことを共有します。」** Website欄は当面 `https://joshu-a.com/`。製品の投稿本文・固定ポストではホームではなく製品の正式URLにリンクする。固定ポストは実製品の公開後に、その製品の価値・対象者・リンクが分かる告知へ差し替える。複数製品が出たら、代表製品か比較できる公式ページを選び直す。公開前に架空の代表製品を固定しない。

画像には説明用の代替テキスト、動画には音なしでも伝わる字幕または本文を付ける。投稿単体でも要点が分かるようにし、URLだけを連投しない。プロフィールの恒久リンクと、投稿ごとの製品リンクを混同しない。[X公式ヘルプ](https://help.x.com/en/managing-your-account/how-to-customize-your-profile)はプロフィールのWebsite欄と固定ポストを案内している。

## note: 背景と検証を読める形にする

書く対象は、開発背景、技術解説、設計判断、失敗と改善、検証結果、製品を理解する助けになる経験。製品広告だけの記事、リンク先の要約だけの記事は作らない。記事単体で読者が判断や実装に使える情報を残す。

1記事の基本構成は **読者の課題 → 前提と制約 → 試したこと・選択理由 → 実物/測定結果 → うまくいかなかった点・限界 → 読者が持ち帰れること → 関連する製品ページへのCTA**。製品との関係が薄い記事ではCTAを無理に置かない。関係が強い長文なら本文で一度だけ文脈に沿ってリンクし、末尾に主CTAを置く。リンク文言は「製品名・できること・何を確認できるか」を示し、単なる「こちら」は避ける。

公式サイトの製品ページは仕様・価格・対応環境・CTAの正本、noteは制作背景や検証の読み物とする。将来、同じ題材を公式Journalにも載せる場合は全文の完全複製を避け、片方を独自の要約・追加情報・導線にする。外部媒体のcanonical制御を前提にしない。検索上の正規URLは公式製品ページ自身に設定し、記事からそこへ通常リンクする。検索結果でどちらが表示されるかは保証できない。[Googleのcanonical説明](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)を参照。noteの[公式ヘルプ](https://www.help-note.com/hc/ja/articles/40855099018777-%E3%82%A2%E3%83%8A%E3%83%AA%E3%83%86%E3%82%A3%E3%82%AF%E3%82%B9-%CE%B2-%E8%A8%98%E4%BA%8B%E3%82%92%E5%88%86%E6%9E%90%E3%81%99%E3%82%8B)には本文リンクのクリック計測が記載されているが、計測機能の利用可否は運用開始時に確認する。

## itch.io: ゲームの発見・プレイ/購入の場

ゲームをitch.ioで扱う場合だけ、ストアページを作る。ページ内で **何のゲームか、誰が楽しめるか、何をするか、操作方法、対応OS・ファイル、価格または無料の扱い、現在の版、画像/動画、問い合わせ先** が分かり、その場で利用・購入・DLを完了できるようにする。タグ、カバー画像、スクリーンショット、説明は実物に合わせる。クレジットや権利情報が必要なら記載する。公式サイトには作品の詳しい説明、FAQ、更新履歴、他製品との関係を置き、ストアから該当製品ページへリンクする。公式製品ページの主CTAは該当するitch.io販売/配布先へ戻す。往復を強制せず、今いるページで必要な行動を完結させる。

更新時はストアの配布ファイル・対応環境・説明を先に直す。devlogはリリースや大きな改善、実測を伴う変更など、単独で読む価値がある場合に使用する。小さな修正はストア上の更新履歴で足りる場合がある。devlog末尾からは必要に応じて該当する公式製品ページへリンクする。Draft/Publicの状態と配布可能性は[itch.io公式ドキュメント](https://itch.io/docs/creators/access-control)に従って公開前に確認する。[ページ作成](https://itch.io/docs/creators/getting-started)、[説明欄の設計](https://itch.io/docs/creators/design)、[devlogと発見](https://itch.io/docs/creators/getting-indexed)も参照。

## 1つの成果から各媒体へ変換する

| 行き先 | 同じ事実の使い方 | 公開条件 |
| --- | --- | --- |
| 公式製品ページ | 対象者、機能、価格・環境、実画面、更新履歴、CTAを正確に更新する | 公開URLと行動先が揃う |
| X短文 | 一番大きな利用者価値を1点だけ伝える | 事実とリンクが確認できる |
| X画像/動画 | 実画面で変化を1つ見せる。本文で何を見てほしいか書く | 公開可能な素材がある |
| note記事 | 問題、選択、失敗、測定、限界を説明する | 深掘りできる一次情報がある |
| itch.io更新 | ゲーム利用者に必要な変更、版、配布ファイル、ストア説明を更新する | itch.ioで扱う実ゲームである |

基本順序は **事実と素材の確認 → 製品/ストアの実体とCTAを公開 → 外部リンクを動作確認 → 媒体ごとに原稿を変換 → 人が承認して投稿 → 結果を記録**。note記事やitch.io devlogは毎回必須ではない。公開前デモなら「開発中」を明記し、まだ存在しない製品ページやDL先へ送らない。公開後に必要なら正式URLへリンクする。

## 入力項目ベースの投稿テンプレート

以下は文面の定型句ではなく、原稿を作るための入力。`URL` は読者が次に取るべき行動の到達先。製品の外部告知では原則 `PRODUCT_URL`（UTM付き）を使い、ストア内の購入/DL誘導は実ストアURLを使う。`MEDIA` は実際の素材と説明文を含む。該当しない媒体の原稿は作らない。

| 種類 | 入力項目（任意は明記） | 変換の焦点・CTA |
| --- | --- | --- |
| 製品リリース | `PRODUCT_NAME`, `TARGET_USER`, `ONE_LINE_VALUE`, `KEY_ACTION`, `PRODUCT_URL`, `AVAILABILITY`, `PRICE`, `PLATFORMS`, `MEDIA` | 何の商品か・誰向けか・今どこで利用できるか。Xは1価値、noteは背景がある場合のみ、itch.ioは実ゲームだけ。 |
| 大型アップデート | `PRODUCT_NAME`, `VERSION`, `CHANGE_SUMMARY`, `USER_BENEFIT`, `BEFORE_AFTER_OR_DEMO`, `PRODUCT_URL`, `RELEASED_AT` | 変化を実画面/根拠で示し、更新済み製品ページへ。 |
| 小型アップデート | `PRODUCT_NAME`, `CHANGE_SUMMARY`, `USER_BENEFIT`, `PRODUCT_URL`、任意で `VERSION` | 利用者に見える変化がある場合だけ短く告知。 |
| 技術的な発見 | `PROBLEM`, `METHOD`, `OBSERVATION`, `LIMITATION`, `EVIDENCE`、任意で `RELATED_URL` | 再現条件・失敗/限界まで示す。関連製品がなければ無理に製品CTAを付けない。 |
| 開発途中のデモ | `PRODUCT_NAME`, `DEV_STATUS`, `DEMO_ACTION`, `VISIBLE_RESULT`, `MEDIA`、任意で `RELATED_URL` | 「開発中」を明示。予定や販売を確約しない。公開先がなければURLは省略。 |
| 不具合修正 | `PRODUCT_NAME`, `VERSION`, `USER_IMPACT`, `FIXED_BEHAVIOR`, `RELEASED_AT`, `SUPPORT_OR_PRODUCT_URL` | 影響と修正済みかを明記。利用者に影響がない内部修正は通常投稿しない。 |
| note記事告知 | `ARTICLE_TITLE`, `READER_PROBLEM`, `ONE_FINDING`, `ARTICLE_URL`、任意で `RELATED_PRODUCT_URL` | Xから記事へ。記事本文は実製品に関連する場合だけ製品ページへ。 |
| itch.io更新告知 | `PRODUCT_NAME`, `PLAYER_BENEFIT`, `ITCH_URL`, `PRODUCT_URL`, `RELEASED_AT`、任意で `VERSION` | Xからは内容に合う行き先へ。itch.io内ではプレイ/DL導線を優先し、公式詳細も相互リンク。 |

`PRICE` や `PLATFORMS` が未確定の製品リリース原稿は公開しない。「未定」は確認済みの開発中デモでは使えても、利用可能な製品の購入判断材料の代わりにならない。`RELATED_URL` は任意であり、架空の製品リンクを補完しない。

## 将来の原稿生成に渡す最小レコード

過剰なCMSは作らない。1回の更新につき、次の項目を一組の入力として持てばよい。ここではデータ形式を固定せず、将来A.I. TERMINAL等が読む際に同じ意味を維持する。

| 項目 | 意味 |
| --- | --- |
| `PRODUCT_NAME`, `SLUG`, `VERSION` | 実製品と今回の版。版番号がない制作記録では `VERSION` は省略可。 |
| `UPDATE_TYPE` | `launch` / `major` / `minor` / `fix` / `demo` / `learning` のいずれか。 |
| `CHANGE_SUMMARY`, `USER_BENEFIT` | 検証済みの変化と、利用者にとっての意味。 |
| `EVIDENCE` | 実画面、変更履歴、測定方法/結果など、主張を確認できる根拠。 |
| `PRODUCT_URL`, `STORE_URL` | 実際に公開済みの正式URL。開発中デモ・技術的な学びでは `PRODUCT_URL`、ストアを使わなければ `STORE_URL` を省略可。 |
| `MEDIA` | 実素材の場所、代替テキスト/字幕、利用許可。素材が不要なら空。 |
| `RELEASED_AT` | 実際の製品・更新公開日時。未設定ならリリース/更新済みとは告知しない。実物の開発中デモは状態を明示して投稿可。 |
| `PUBLISH_ALLOWED` | 人が事実・権利・公開時期を確認した可否。初期値は `false`。 |
| `CHANNEL_STATUS` | 媒体ごとに `skip` / `draft` / `approved` / `published` と公開URL（公開済みの場合のみ）。 |

自動化してよいのは、レコードの欠損確認、媒体に合わせた草稿生成、長さ・リンク/UTM・素材の存在確認、同一事実からの要約候補、公開状態の記録。自動化すべきでないのは、投稿価値の最終判断、主張の真偽/測定解釈、権利・秘密情報の確認、炎上や誤解の文脈判断、公開時期の決定、外部アカウントへの実投稿。`PUBLISH_ALLOWED` と各媒体の `approved` は人が確認してから設定する。承認済みでも投稿の実行は別の明示的な運用判断とする。

## URL・UTM・計測

- 投稿からの既定の送客先は **該当製品ページの正式URL**。公開前で製品URLがない場合はURLを捏造しない。note記事の告知は記事URL、itch.io内で今すぐ購入/DLさせる案内は実ストアURLを優先する。
- 公式サイト内のリンク、canonical、OG URL、sitemap、検索結果用URLにはUTMを付けない。外部媒体から公式製品ページへのリンクにだけ付ける。
- `utm_source`: `x` / `note` / `itchio`。将来の媒体は短い一貫した小文字名を追加。
- `utm_medium`: Xは `social`、note・itch.ioは `referral`。媒体ごとに表記を増やさない。
- `utm_campaign`: 公開告知は `<slug>-launch`、大型更新だけ `<slug>-update-YYYYMM` に切り替える。小型更新では既存キャンペーンを使い、投稿単位で細分化しない。同じ施策なら各媒体で同じ値を使う。[製品公開手順](product-launch.md)と揃える。
- 例: `https://joshu-a.com/products/<slug>/?utm_source=x&utm_medium=social&utm_campaign=<slug>-launch`。`<slug>` は実公開製品の値に置き換える。URLを公開前に実際に開いて確認する。

評価は **媒体露出 → 製品ページ到達 → 主CTAクリック → DL/購入/利用** の順。最初はリンク到達とCTAが動くかを確認し、利用可能な計測が整ったら媒体/キャンペーン別の到達数・CTA率・完了数を見る。noteのリンククリックやitch.io側の数値は利用できる場合だけ補助指標にする。フォロワー数、インプレッション、投稿数は診断用であって目標の中心にしない。計測できない段階では数値を推定しない。

## 現時点のサイト判断と製品公開時の確認

2026-10-06時点の`main`には未公開の実製品ページがなく、ホームページに公開準備中の説明、基本的なOG/X情報、製品領域がある。外部チャネル運用のために今すぐ必要なサイト側P0/P1の追加実装はない。空のSNS枠、Journal、架空の製品カードは作らない。

最初の製品公開時は、正式製品ページ、実際の価格/対応環境/画像、canonical/OG/X、主CTAと行動先、ホームからの製品導線、必要なsitemap登録を揃えて動作確認する。その後、媒体プロフィールと投稿にディープリンクを設置する。外部投稿が先に出てリンク先が未完成になる順序は避ける。
