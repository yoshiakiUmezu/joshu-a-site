# 助手A サポート運用

製品公開後の問い合わせを、個人開発の負担を増やさず処理するための内部手順。現在の連絡先は `contact@joshu-a.com`。実際のメール送信、サポート用アカウントやフォームの追加はこの文書では行わない。応答時間や解決時間を約束しない。

## 問い合わせ分類

受信時は主分類を1つだけ付ける。複数の話題がある場合は主な解決目的を選び、必要なら補足タグを付ける。

| 分類 | 含める内容 |
| --- | --- |
| 一般・購入前 | 一般問い合わせ、購入前の機能・価格・対応環境の質問 |
| 利用・技術サポート | 購入後質問、起動・操作、ダウンロード、更新、不具合報告 |
| 購入・ライセンス | 購入確認、支払い、返金、ライセンス。販売ストアが窓口なら該当ストアへ案内 |
| プライバシー・権利 | 個人情報に関する依頼、著作権・権利侵害の連絡。通常の問い合わせから分けて人が確認 |
| 取材・紹介 | 取材、レビュー、掲載、提携など |
| 対応不要 | スパム、営業一斉送信、製品と無関係な連絡 |

## 窓口と受け付ける情報

当面は`contact@joshu-a.com`一本で運用する。問い合わせ量、担当者、対応方針を分ける必要が出るまでは`support@`、`privacy@`、`legal@`やフォームを増やさない。分離を検討するのは、対応漏れが繰り返す、複数人で担当する、機微なプライバシー依頼を分離・監査する必要が生じる、またはストア・法令が専用窓口を求める場合。

不具合の再現に必要な範囲で、次を任意で聞く。

- 製品名とバージョン、入手元（公式サイトまたはストア）
- OS名・バージョン、必要な場合だけ端末/機種
- 起きたこと、期待した結果、再現手順
- 表示されたエラーの正確な文面
- 画面画像やログは、文章だけで再現できない場合に限り任意で依頼

まず受信文から分かる情報を使い、同じ内容を聞き直さない。名前、住所、電話番号、年齢、アカウントID、シリアル番号などは原則求めない。パスワード、認証コード、APIキー、決済カード番号・セキュリティコード、秘密情報は絶対に送らせない。

ログや画像にメールアドレス、氏名、端末ID、ファイルパス、トークン、Cookie、認証情報、他人の情報が入ることがある。送信前に伏せるよう案内し、必要な箇所だけの短い抜粋を依頼する。機密情報を含むログを通常メールや公開GitHub Issueに転送しない。受け取ってしまった場合は不用意に複製・転送せず、人が削除やインシデント対応の要否を判断する。

## 優先度

優先度は初期判断であり、自動分類だけで確定しない。影響範囲・再現性・回避策を見て人が調整する。返信期限やSLAは掲げない。

| 優先度 | 例 | 初動 |
| --- | --- | --- |
| P0 | データ消失・漏えいの疑い、認証/セキュリティ問題、全体的な起動不能、購入・配布が広範囲に不能 | すぐ人へエスカレーション。影響する公開・配布・決済の一時停止が必要か判断し、事実と時刻を記録。原因や被害を推測で公表しない |
| P1 | 主要機能が使えない、複数ユーザーに影響する不具合、重要な更新失敗 | 再現・影響範囲を優先確認し、既知Issueと照合。回避策または次の確認事項を案内 |
| P2 | 個別環境の不具合、限定的な機能問題、回避策がある | 必要最小限の環境・再現情報を確認し、通常の調査候補へ |
| P3 | 機能要望、軽微な表示問題、一般的な質問 | 要望・質問として記録。回答や実装を約束しない |

購入不能が一人の環境かストア全体か分からない場合は、影響範囲を確認するまで仮の優先度にする。返金の可否や金額はサポート側で確定せず、販売ストアまたは実際の販売主体へつなぐ。

## 返信草稿の入力項目

毎回ゼロから定型文を選ぶのでなく、確認できた事実と次の手順を次の項目にまとめてから短い返信を作る。空欄を推測で埋めない。

```yaml
CASE_ID: internal-reference-only
PRODUCT_NAME:
ISSUE_TYPE: general | presales | usage | bug | download | update | purchase | refund | license | privacy | rights | press | spam
PRIORITY_CANDIDATE: P0 | P1 | P2 | P3
VERSION:
ENVIRONMENT:
FACTS_CONFIRMED: []
MISSING_INFO: []
KNOWN_ISSUE:
WORKAROUND:
STORE_SUPPORT_URL:
SUPPORT_URL:
NEXT_ACTION:
FOLLOW_UP_QUESTION:
REPLY_PURPOSE: received | request-info | known-issue | fixed | no-fix | unsupported-env | store-routing | privacy | rights | resolution-check
HUMAN_REVIEW_REQUIRED: true
```

返信の種類ごとに入力する要点:

| 用途 | 入力・伝える内容 |
| --- | --- |
| 受領確認 | `PRODUCT_NAME`, `ISSUE_TYPE`, `NEXT_ACTION`。受け取ったことと、次に確認する内容だけ伝える |
| 情報不足 | `FACTS_CONFIRMED`, `MISSING_INFO`, `FOLLOW_UP_QUESTION`。必要な項目をまとめて尋ね、任意情報と伏せるべき情報を区別 |
| 既知の不具合 | `KNOWN_ISSUE`, `WORKAROUND`, `NEXT_ACTION`。該当バージョンと既知の範囲を照合して案内 |
| 修正済み | `VERSION`, 修正内容、適用手順、確認方法。修正が配布済みと確認できた場合だけ「修正済み」とする |
| 修正予定なし | 確認した事実と現時点の判断、代替手段。予定や理由を捏造しない |
| 利用環境対象外 | `ENVIRONMENT`, 対応範囲、確認可能な代替環境。対象外だけを理由に即時打ち切らず、再現できる範囲を明記 |
| 購入・返金 | `STORE_SUPPORT_URL`, 注文を特定せずに案内できる一般手順。販売ストアの窓口へ誘導 |
| プライバシー | `REPLY_PURPOSE`, `NEXT_ACTION`。受領確認に留めて担当者へ回し、本人確認・削除等を自動確定しない |
| 権利関連 | 受領確認と人の確認先。法的結論、削除要求への承諾・拒否を自動回答しない |
| 解決確認 | 修正/案内後の結果確認。返信がないことを解決済みと記録しない |

## 自動化と人の確認

将来のAI補助は、受信内容を必要最小限にして分類、製品・バージョン抽出、不足情報の候補出し、既知Issueとの照合、重複候補、優先度候補、返信草稿、Issue候補、FAQ候補、対応履歴の要約までを行える。分類の確信が低い場合は「不明・要確認」とする。メール本文やログをAIサービスへ渡す場合は、送信先・保存・学習利用等を管理者が確認し、不要な個人情報・秘密情報を除いてから扱う。

以下は自動確定・自動送信しない。内容を人が確認する。

- 返金・補償・販売主体・契約や法律上の主張
- プライバシー権利行使、本人確認、データ削除・開示
- セキュリティ事故、漏えい、脆弱性の深刻度と公開判断
- アカウント・決済情報の取得、保管、変更
- 権利侵害の受理・削除・異議申立てに関する判断
- 公開謝罪、声明、報道・取材回答
- GitHub Issueやメール等の外部送信・公開の最終実行

## 不具合から開発への接続

1. 問い合わせを分類し、製品・バージョン・環境・再現手順を必要な範囲で整理する。
2. 個人情報、秘密情報、不要なログを除き、既知Issue・過去の対応と重複がないか確認する。
3. 再現手順、期待結果、実結果、環境、影響範囲、優先度候補だけでGitHub Issueの**草稿**を作る。元メールや個人情報を貼らない。
4. 人が内容・公開範囲・優先度を確認してからIssueを作成する。公開リポジトリでは特に、報告者を特定できる情報を含めない。
5. 修正・検証結果・対象バージョンを記録し、配布されたことを確認してから報告者へ返信する。
6. 解決確認を尋ねる場合も、返答がないことを解決と扱わない。

理想フローは「受信 → 分類 → 再現情報整理 → 重複確認 → Issue候補 → 人が優先度/公開範囲を判断 → 修正 → 検証・配布 → ユーザー返信」。GitHub Issue作成と返信送信は、将来のA.I. TERMINAL連携でも承認境界を残す。

## FAQへ昇格する基準

同じ質問が別の利用者から繰り返された、購入判断に重要、初回利用でつまずきやすい、または安全な回避策を定型化できる場合にFAQ化を検討する。1件だけでも重大な誤解やデータ損失防止に関わる場合は、公開FAQの価値を人が判断する。問い合わせ内容の転載や個人情報の引用はしない。回答が製品の仕様・サポート範囲と一致することを確認し、FAQを追加しても公開ページや製品説明の正本を更新する。

## サポート対象外・確認範囲

サポート対象外の環境は、製品ページで分かるようにする。対象外OS、非対応端末、改造版、非公式ビルド、自己改変ソース、ストア外入手、root/jailbreak等では、保証や再現を約束しない。ただし一律拒否はせず、公式配布版・対応環境で再現するか、既知の問題か、簡単な安全な回避策があるかを可能な範囲で確認する。再現に個人情報・決済情報・危険な設定変更を求めない。

外部ストアやネットワーク障害が疑われる場合は、確認できる公開ステータスとエラー時刻を案内し、ストアの購入・返金窓口へ誘導する。外部サービスの原因を確証なく断定せず、サービス復旧後の再試行で解決するかを確認する。

## エスカレーションと公開前確認

P0候補、データ消失・漏えい・脆弱性の疑い、権利侵害、プライバシー権利行使、返金・契約・法的主張は通常の回答フローから分け、人が確認する。必要な法務・プライバシー判断は[製品公開時の法務チェック](legal-release-checklist.md)に従い、自動で適法/違法を断定しない。

製品公開前に、`contact@joshu-a.com`の受信・返信、製品ページと販売ストアの問い合わせ先、返金関連の正しい窓口、対応OSと既知Issueの案内方法を人が確認する。実製品未公開の段階でSupportページやフォームは作らない。
