# 助手A Commercialization Playbook

Last updated: 2026-10-06

## 目的

A.I. TERMINALで実製品が完成したあと、販売開始までのタイムラグを極小化する。

目標:
- 製品完成後、販売条件が既知なら **24時間以内に公開・販売開始可能** な状態を維持する。
- サイト制作や販促準備を製品完成後にゼロから始めない。
- 販売判断は「製品ごとに毎回悩む」のではなく、共通ルールから例外だけ判断する。
- 最初の事業目標は **Pro 100費用を支払っても余剰が残る状態**。その後、月5万円純利益、さらに上を目指す。

## 収益目標ステージ

### Stage 1 — Pro 100余剰ライン
- Pro 100を固定費として吸収し、月次で余剰が残る。
- 「払える」ではなく「継続しても事業収支を圧迫しない」ことを重視する。
- 最初の販売検証では、売上額だけでなく販売数・CV・サポート負担も見る。

### Stage 2 — 月5万円純利益
- Pro 100費用を差し引いた後でも十分な余剰がある状態。
- 単一商品依存か、複数商品で安定しているかを確認する。

### Stage 3 — さらに上
- 月10万円以上を次の目安とし、上位Proや追加投資は「追加固定費以上の生産性/利益を生むか」で判断する。

## 製品完成から販売までの標準フロー

### T+0〜2時間: 販売判定
製品完成時に次を確定する。

1. 製品カテゴリ
   - Software
   - Game
   - Experiment / small tool

2. 提供形態
   - 無料
   - 買い切り
   - 無料版 + 有料版
   - DLC /追加コンテンツ

3. 対応環境
   - Windows
   - Android
   - Web
   - Steam等

4. 公開条件
   - 署名
   - ストア審査
   - テスター要件
   - 外部アカウント要件
   - 法務/権利確認

5. 人手負担
   - 公開時のみ
   - 継続保守
   - 問い合わせ
   - 定期更新
   - 外部審査対応

この時点で「人手が継続的に必要」「資格/法規制が重い」「有料外部APIが必須」なものは、販売優先度を下げる。

### T+2〜6時間: チャネル選択

#### 原則
- **公式サイトは母艦。**
- Discoveryが強い外部チャネルは入口として使う。
- 同じ製品を無理に全チャネルへ出さない。
- 審査・人手負担が大きいチャネルは、期待収益が上回る場合だけ使う。

#### Software
優先候補:
1. joshu-a.com 製品ページ
2. Web直配布 / Windows配布
3. itch.io（DL商品と相性が良い場合）
4. note（製品そのものではなく説明・導線）
5. その他ストアは製品適合性と審査負担で判断

#### Game
優先候補:
1. joshu-a.com 製品ページ
2. itch.io
3. Steam（製品価値・完成度・市場適合が十分なら）
4. X / note はDiscovery補助

#### Android
Google Playを使う場合は、その時点の個人アカウント要件・テスト要件を再確認する。
人手要件が大きい場合はWeb/Windows/itch.io等の代替チャネルを先に検討する。

### T+6〜12時間: 価格決定

価格は「開発時間の回収額」だけで決めない。

最低限、以下で決める:
- 顧客が得る価値
- 代替製品の相場
- 購入判断の摩擦
- ストア/決済手数料
- 税・返金・サポート負担
- 想定販売数
- アップデート義務
- ブランド初期の認知不足

#### 価格ルール
- 初期商品は「安ければ売れる」を前提にしない。
- 値下げより、価値説明・デモ・対象ユーザーの明確化を先に行う。
- 販売数が少なくても利益が残る価格を優先する。
- 買い切りを基本候補とし、サブスクは継続価値と運用体制が必要な場合だけ検討する。
- 価格確定時には最新の競合価格・手数料を再調査する。

### T+12〜18時間: 販売ページ・素材
ホームページ制作側へ渡す必須入力:
- product slug
- 製品名
- 一文価値
- 対象者
- 価格
- 対応OS
- 提供先URL
- 主要機能/体験
- スクリーンショット/動画
- FAQ
- サポート先
- 更新方針

販促側は「何を書くか」を決め、HTML/CSS実装はホームページ側へ渡す。

### T+18〜24時間: Discovery開始
製品特性に応じて必要なものだけ実施。

- itch.io: ストアページ公開
- X: リリース/デモ投稿
- note: 制作背景・検証・問題解決など、単体でも価値がある記事
- 検索: sitemap / Search Console確認
- 公式サイト: 製品ページを正本として各外部チャネルからディープリンク

## チャネル採用判断

各チャネルを次の5項目で判定する。

| 項目 | 質問 |
| --- | --- |
| Discovery | 新規ユーザーに見つけてもらえるか |
| Conversion | 購入/DLまで自然につながるか |
| Margin | 手数料後も利益が残るか |
| Human Cost | 審査・更新・投稿・問い合わせが重くないか |
| Automation | A.I. TERMINAL / Work / dotで将来どこまで自動化できるか |

原則:
- Discoveryが弱くてもMarginとAutomationが高ければ母艦として採用。
- Discoveryが高くてもHuman Costが大きすぎる場合は後回し。
- 継続的な手作業が必要なチャネルは、その作業コストを利益計算に含める。

## 販売後72時間で見るもの

販売後すぐに「売れた/売れない」で製品を切らない。

最低限:
- 製品ページ流入
- CTAクリック
- ストア/配布先到達
- 購入/DL
- 流入元
- 問い合わせ/不具合
- 価格への反応
- 離脱箇所

判断:
- 流入がない → Discovery問題
- 流入はあるがCTAが押されない → 価値説明/価格/信頼問題
- CTAは押されるが購入されない → ストア/価格/提供条件問題
- 購入されるがサポート負荷が高い → 商品設計/保守問題

## やらないこと

- 製品完成後に販売チャネルをゼロから調査する。
- 全チャネル同時展開を目的化する。
- SNS投稿本数をKPIにする。
- 薄いSEO記事を量産する。
- 売上だけを見て手数料・保守・人手を無視する。
- サブスクを理由なく採用する。
- 公開前に架空のレビュー・導入実績・評価を置く。

## 現在の待機状態

実製品が確定するまでは:
- チャネル/価格ルールを維持
- 最新の手数料・審査要件は製品確定時に再調査
- サイト側は製品入力待ち
- 販促側は販売開始までのタイムラグを増やす未準備がないか定期確認する
