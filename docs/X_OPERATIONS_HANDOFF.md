## 安全・GitHubルール

- メインの情報源はGitHubの正本文書。会話履歴・AIの推測を恒久的な状態管理に使わない。
- リポジトリ更新は **最新main + 進行中PR確認 → 担当専用ブランチ → Draft PR**。main直接push、force push、他担当のブランチ再利用は禁止。
- `joshu-a-site` はmainとCloudflare Pages本番公開が連動している。無承認mainマージは不可。
- 外部アカウントのプロフィール変更、固定ポスト、投稿、公開URLの変更、有料サービス利用はユーザー承認を得る。
- 人手負担最小化を優先。毎日投稿や有料自動化を前提にせず、実績に基づいて少数投稿する。
- X投稿データの正本化にあたって、アクセス用トークン、ログイン情報、個人情報は記録しない。
- X担当が運用を開始したら、このファイルのステータスと未完了項目を更新し、他の窓が同じ状態を読めるようにする。

矛盾がある場合は担当範囲の正本を優先し、変更を必要とする他担当の文書を無断で上書きしない。変更の提案/事実報告を送ってから担当が反映する。古い日付・旧HEADの状態を現在の事実として転記しない。

### 更新タイミングと書く内容

- 新規の重要な決定、プロフィール/固定ポストの最終稿、素材の所在確認、公開承認、投稿完了、運用条件変更、ブロッカー解消があったときに更新する。
- 日常の思いつきや下書き段階は「提案」「未決定」と明記し、承認済みルールにすり替えない。
- 冒頭の `Status` と `Updated` を更新し、「完了」「進行中」「承認待ち」「次の作業」を最新化。必要に応じて作業の根拠（公開URL、PR、HEAD、スクリーンショット/動画版、日時、実行主体）を添える。
- 公開済み・投稿済みの記録は、投稿URLやアカウント画面などの実証があるときだけ記載。本人の操作が完了したか見られない場合は「報告待ち」「未確認」。
- トークン、Cookie、認証情報、個人情報、内部画面の秘密情報はGitHubに保存しない。
- 新しい運用判断をすべて別MDに分割しない。既存文書に収まる内容ならそこを更新し、同じルールを複数文書へ重複させない。

### GitHub作業順序と競合防止

1. 作業開始時、`main` と進行中のPR・担当ブランチ・対象ファイルの最新差分を確認する。
2. **この引き継ぎ文書は最初 `docs/x-operations-handoff-20261009` ブランチにのみ存在する。** `main` へマージされていない時点で `main` から読めないことを「消失」と誤認しない。まずブランチ上の実ファイルを参照する。
3. 初回は専用ブランチの内容をレビューして文書PRを作成/引き継ぎ、レビュー後に承認手順を経て `main` に反映する。既存PRがあれば重複作成しない。
4. 正本化後の変更は最新 `main` 起点の **X担当専用ブランチ → Draft PR → 差分/リンク検証 → 所定の承認 → merge** で反映する。複数担当が同じMDを同時に編集しない。最新の同名ファイルがある場合は先に差分を照合する。
5. `main` への直接push、force push、他担当の作業ブランチ更新、未承認のマージは禁止。 `main` はCloudflare Pages本番と連動するため、文書だけのPRでも公開影響を確認する。
6. マージ後は `main` から実際に文書を読めることを検証し、以後はその正本を参照する。Draft/未マージの内容を「全窓共有済み」と表現しない。

### 他窓との情報共有

- Xの原稿・動画・投稿実績はこの文書で記録し、販促窓には成果とURLだけを共有する。

- 公式サイトのリンク・文言・公開状態に変更が必要ならホームページ窓へ依頼する。X窓からサイト共通ファイルを直接編集しない。
- A.I. TERMINALのロゴ・起動アニメーションの正本はA.I. TERMINAL側。資料の読み取りや収録についてのみ協議し、開発窓の本来の優先作業を妨げない。
- 新しいX運用窓への移転時は、正本のURL、参照すべきブランチまたは `main`、保留事項、最新の投稿/PR証拠を簡潔に伝える。
