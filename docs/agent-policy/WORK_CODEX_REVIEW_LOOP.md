# 助手A 標準開発ループ — Work → GitHub → 同一Codexスレッド → Work検収

状態: **運用方針の正本候補**（2026-11-13）。対象リポジトリで有効化・実行を確認するまで「自動化済み」と記載しない。

## 適用範囲

- 対象: ユーザーが開発対象として指定したソフトウェア／ゲーム。KNOCK BACKで相互検知を実証した方式を再利用する。
- **除外**: `yoshiakiUmezu/ai-terminal`、dots（助手B）の実装・監査・自走ループ、`btc-research`等の投資研究、運用監視専用リポジトリ。A.I. TERMINAL完成後の移行は別判断。
- 本書は `COMMON_RULES.md` と**別の任意適用規約**。共有ブロック同期に組み込まず、除外対象のAGENTS.mdを書き換えない。
- 安全・費用・品質・ユーザー承認の既存ゲートと矛盾する場合は、より厳しい条件を優先する。

## 1回の開発サイクル（標準）

1. **Work（設計）**: 現行コード・正本仕様・既存PRを見て、範囲、差分、受入条件、実機／手動でしか分からない条件、停止条件を明示した指示MDをGitHubに提案する。状態は `proposed`。レビュー担当と実装担当は分離する。
2. **ユーザー承認**: 明示的な承認を確認した指示だけ `approved` にする。ユーザーに見せないまま次の実装を開始しない。「既存タスクのFAIL修正」は新規工程でない限り、承認済み範囲内で再実装できる。
3. **既存Codexスレッド（実装）**: プロジェクト専用の**同じスレッド**に紐づくThread automation/heartbeatが、リポジトリの**指示一覧**とPRレビューを定期巡回する。タスクIDや単一指示ファイルを固定監視しない。PASS後も巡回を削除せず、未処理指示がなければ何もしない。作業前に既存PRを検索し、同じタスクの二重起動を避ける。コード・正本仕様・承認状況は毎回最新のGitを参照し、会話履歴のみを正としない。
4. **PR提出**: Codexは承認範囲内の実装、最小限の検証、証跡記録を1件の関連PRにまとめ、ready for reviewとする。レビュー基準はタスクMD。ブランチとPRの対応を明示する。未実施の実機・視聴覚確認はPASSとして申告しない。
5. **Work（検収）**: 当該リポジトリのPR ready_for_reviewとコミット更新（synchronize）を契機に実diff、成果物、テスト証拠、設計MDを照合して `PASS`/`FAIL`/`UNKNOWN` をPRコメントに残す。FAILなら同じPRに具体的修正依頼を返す。UNKNOWNは証拠・アクセス不足等を明示し、成功扱いしない。
6. **再実装ループ**: Codexは同じスレッドの巡回でFAILを取得し、**同じPR**へ範囲内の修正を追加する。更新イベントでWorkが再検収。本人の別途許可なく対象範囲や課金を広げない。
7. **次案・人間の決定**: PASS後のWorkは次の**最小で具体的な1案**（目的・範囲・受入条件・リスク）をユーザーへ提示する。**ユーザーがOKするまで次の指示はapprovedにしない**。合格しても自動マージ・公開・配布は個別の既存権限に従う。

## 監視対象を固定して再設定を不要にする

- 各リポジトリに**1つの指示一覧**を設ける。初期推奨パスは `docs/agent-loop/README.md`、指示は `docs/agent-loop/tasks/<TASK-ID>.md`。既存のKNOCK BACKは `docs/automation-pilot/README.md` を当面継続し、並列キューを作らない。
- Codexの巡回対象は指示一覧だけ。Work側はPRイベントのうち管理対象タスクのタイトル／指示IDだけを検収する。新しい工程ごとに両者のAutomationを削除・作成しない。
- 指示状態は `proposed` / `approved` / `in_progress` / `review` / `pass` / `blocked` のいずれかとし、同じ完了状態を複数の正本に複製しない。既存リポジトリの工程MDを正本とする場合は、それに合わせる。PR・コミット・レビューコメントが実際の状態証拠。
- FAILの修正待ちは同じタスク・PRを再開し、最新のWorkコメントを必ず確認。未処理IDの重複実行、PASS済みIDの再実行は禁止。
- 原則として新規ユーザー設定は**各案件の初回プロビジョニング1回だけ**。以後は承認された指示MDを登録するだけ。プロジェクト間で同一のCodexスレッドを使い回さない。

## 新規プロジェクト導入・初期設定をユーザーへ押し付けない

導入担当はWorkを第一候補とする。ユーザーが対象を承認したら、**導入担当が**GitHub内の指示一覧と規約リンク、既存Codexスレッドの有無、Thread automationの有効化、WorkのPRイベント検収設定を確認・可能な範囲で自分で設定し、初回に実イベントが届いた証拠を残す。**毎工程ユーザーへ設定指示を投げない。**

ただしGitHubのMarkdownだけではCodexへのheartbeat作成やWorkイベント購読は開始しない。**既存スレッド作成やautomation設定が利用可能な道具から実行できなければ、未設定として止め、唯一必要な本人操作と代替案を短く報告する。** 他人が自動化設定済みと記載しただけでは有効化済みと扱わない。

新規作成リポジトリは可能なら共通AGENTSテンプレート＋本規約へのリンクを最初から含める。テンプレートが使えない場合も、明示許可なくAPI課金・GitHub Actions起動・外部サービス導入で代用しない。

## 品質と安全

- **連携の合格**（検知→PR→検収→同PR修正→再検収）と**成果の品質合格**を分ける。前者の成功は造形・音・動作の成功を保証しない。
- 画面・3D・音・実入力・パフォーマンスを問う受入は、その証拠を確認できた範囲だけ評価。コードレビューで実機検証を代替しない。
- KISS、必要最小限のテスト、境界で1回の入力検証、未承認の変更禁止、機密保護を既存規約どおり維持する。
- GitHub Actions、APIキー、追加料金、公開・デプロイ・自動マージ等は**導入のために勝手に始めない**。リポジトリの個別規約・最新ユーザー承認を優先。
- 導入状態は `not_configured` / `repo_ready` / `codex_ready` / `review_ready` / `e2e_confirmed` の区別で実証する。Git文書追加だけで `e2e_confirmed` にしない。

## 先行検証と境界

KNOCK BACKの2026-11-13のPR #31（WorkのPASS）とPR #33（WorkのFAIL→同PR更新→UNKNOWN再検収）は**双方向イベント連携**の証拠。元のCodex実行ログの独立確認と、実際のゲーム品質・実機評価は別項目で継続検証する。A.I. TERMINALを含む全リポジトリへの一斉同期は行わない。
