## 助手A 共通エージェントルール（正式版 v1.1）

正本: `yoshiakiUmezu/joshu-a-site/docs/agent-policy/COMMON_RULES.md`。このブロックは各リポジトリのルート `AGENTS.md` へ同期する。

### 優先順位・進め方
- ユーザーの最新の明示指示、法令・安全条件、リポジトリ固有の確定仕様・作業ルールを尊重する。共通ルールを理由に、既存の承認条件・ブランチ運用・テストゲート・機密保護を緩めない。矛盾があれば勝手に解釈せず報告する。
- 着手時は関連コードと作業内容に応じた正本資料だけを確認する。`AGENTS.md` は恒常的な作業原則と参照先の地図に保ち、詳細仕様・計画・一時的手順は既存の正本資料へ置く。全Markdownの機械的な通読、推測での仕様確定、無関係な修正を避ける。
- 実装済み・検証済み・計画中・未確認を区別する。テスト未実施や代替環境での成功を正式PASSとしない。

### 設計・実装（KISS）
- KISS最優先。現実の要求に必要な最小構成で実装し、将来を仮定した抽象化・汎用基盤・重複状態・過剰な防御コードを増やさない。
- 外部入力など信頼境界で一度検証し、内部処理では型と責務を信頼して同じ検証を繰り返さない。新しい信頼境界、安全上の不変条件や現実の障害は適切に扱う。
- 既存の設計・データ・インターフェースを確認し、変更を局所化する。テストを通すためだけに確定仕様や製品の正しい動作を変えない。
- 重要かつ見落としやすい不変条件は適用範囲と守るべき結果を示し、禁止事項には安全な代替手順を併記する。曖昧な全面禁止や、既存ルールの言い換えを増やさない。
- 論理上は発生し得ても通常運用ではまず起きない例外のために、専用のエラーハンドリング・フォールバック・テストを追加しない。ただし現実の外部障害、入力境界、セキュリティ・データ損失につながる失敗は必要最小限で扱う。

### テスト・文書
- 故障リスクに比例した最小限の検証を選ぶ。過剰なテスト、同じ事実の多層重複テスト、無関係な全件実行は禁止。リポジトリ固有の必須ゲートは優先する。
- 仕様・挙動・インターフェースを変えたら関連する正本Markdownだけを同じ変更で更新し、計画と事実を混在させない。文書だけの変更に無関係なビルドを求めない（個別の必須条件があれば従う）。
- 明示的に許可された作業は、個別の承認条件・修正回数上限・作業範囲を守り、実装→必要な検証→失敗原因への局所修正・再検証まで進める。初回実装だけで完了扱いしない。
- 変更と、実際に実行した検証・未検証事項・残る課題を簡潔に報告する。

### 新規リポジトリの作成
- エージェントが新規リポジトリを作成する場合、最初のコミットからルート `AGENTS.md` にこの共通ブロックを含める。専用テンプレート `yoshiakiUmezu/joshu-a-repo-template` が利用できる場合はテンプレート経由で作成し、初回コミットより後に追加する運用を標準にしない。
- リポジトリ固有ルールは共通ブロックの外に追加する。特定ディレクトリだけに必要な追加ルールは、その配下の `AGENTS.md` に限定し、上位の安全・承認条件を弱めない。不要な分割はしない。GitHub の通常の「New repository」に自動初期化される設定があると誤認しない。

### 安全・費用・Git
- APIキー、認証情報、秘密情報、未公開情報をコード・ログ・Issue・PR・外部サービスへ漏らさない。リポジトリの公開範囲を無断で変更しない。
- **正式リリース前**と確認できるプロジェクトでは、通常の開発PRのマージをその都度のユーザー承認なしに実行してよい。リポジトリ固有の必須テスト・保護ルール・特別な承認ゲートは守り、リリース済み・公開運用中・リリース状態不明のものは自動許可扱いにしない。
- **正式リリース後**のPRマージ、公開・本番デプロイ、課金発生、未承認の外部サービス導入は、事前の明示承認が必要。通常の開発マージ許可はリリース作業・公開操作・販売開始の許可を意味しない。
- force push、履歴改変、未コミット作業の破棄などの破壊的操作を行わない。他の作業者の変更を保持する。
