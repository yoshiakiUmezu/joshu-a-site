# 製品公開・更新時の販促素材

実製品の公開・更新から、必要な画像、動画、媒体別の文章を無理なく用意するための制作ルール。実製品はまだ未公開のため、この文書は仕様だけを定め、製品素材・見本投稿・仮ページは追加しない。

## 既存文書との役割

- [集客・コンテンツ導線戦略](../ACQUISITION_STRATEGY.md): 媒体と製品ページの役割、発見経路の優先度。
- [外部チャネル運用](social-operations.md): 投稿する/しない、X・note・itch.ioの使い分け、UTM、投稿承認。ここでは素材と媒体別原稿の作り方を具体化する。
- [製品公開手順](product-launch.md): 製品情報JSON、ページ生成、OG/screenshot/videoのページへの接続、正式release gate。
- [計測と改善ループ](measurement-improvement.md): 公開後の取得可能な集計、判断周期、改善。

製品ページと製品情報JSONが仕様・価格・対応環境・実URLの正本。販促素材は同じ事実を媒体ごとに見せ直すもので、製品ページと異なる価格や機能を持たせない。ソフトウェアやゲームに関係するサポート・ライセンス等の表示判断は[法務・プライバシーチェック](legal-release-checklist.md)、問い合わせ情報の扱いは[サポート運用](support-operations.md)に従う。

## 素材は成果に合わせて選ぶ

| 素材/用途 | 理解させること | 作る条件・基本リンク |
| --- | --- | --- |
| 製品ページ紹介文 | 何の商品か、誰向けか、できること、価格/環境、次の行動 | 正式公開の製品情報。CTAは実際の販売/DL/利用先 |
| OG画像 | 外部共有カードだけで製品名と視覚的特徴が伝わること | 製品ページに専用画像を設定。ホーム用OGを製品用に流用しない |
| 製品スクリーンショット | 画面/プレイ内容と主要体験 | 内容を説明する画面があるとき。製品ページやitch.io等のストアにも必要分だけ掲載 |
| 短いデモ動画 | 1操作または1場面の変化 | 動きが静止画より理解を助ける場合。製品ページ、X、itch.ioから必要なものを選ぶ |
| X短文 | 1つの成果・変更とユーザー価値 | リリース、重要更新、分かりやすい実画面、実測/技術知見等。関連ページ/記事にリンク |
| X画像付き投稿 | 画面の見どころ1点 | 静止画の方が伝わる成果。説明とaltを添える |
| X短尺動画投稿 | 動く操作/結果 | 1クリップで伝わる実画面。音なしで理解できる本文/字幕を添える |
| note記事 | 課題、判断、試行、結果、限界から読者が得られる知識 | 背景や検証に独立した価値があるときだけ。記事告知は別の短文で記事へリンク |
| itch.io告知/更新文 | プレイヤーが今できることと公開ファイル/更新点 | itch.ioで実際に扱うゲームのみ。購入/DLがそこで完結するなら直接ストアへ案内 |

告知は次の種類に整理する。

| 告知 | 用途 | 必要な事実 |
| --- | --- | --- |
| リリース告知 | 初公開を案内 | 公開済み状態、購入/DL/利用先、価格・対応環境 |
| 大型更新告知 | 主要な体験/機能の変化を示す | バージョン、利用者への利益、更新済みか |
| 不具合修正告知 | 利用者への影響と修正を明確にする | 対象バージョン、影響、修正公開日、回避策の有無 |

全媒体へ展開することを成果の完了条件にしない。小さな内部修正は製品の更新情報に記録するだけでよい。note、動画、itch.io告知は、それぞれに独立した利用者価値があるときだけ作る。

## 1回の更新にまとめる共通入力

[social-operations.md](social-operations.md)の将来の更新レコードを正本として再利用する。既存項目を別仕様に置き換えず、次のように補う。

| 項目 | 用途/規則 |
| --- | --- |
| `PRODUCT_NAME`, `SLUG`, `VERSION`, `UPDATE_TYPE` | 実製品と実バージョン。`launch` / `major` / `minor` / `fix` / `demo` / `learning`等。 |
| `TARGET_USER`, `ONE_LINE_VALUE`, `KEY_ACTION` | 誰向けで、何の役に立ち、何をすると結果が得られるか。変更告知では前回からの差分を優先。 |
| `CHANGE_SUMMARY`, `USER_BENEFIT`, `EVIDENCE`, `LIMITATIONS` | 実際の変更、利用者価値、主張を確認できる根拠、対象外条件/限界。未計測の性能値を含めない。 |
| `PRODUCT_URL`, `STORE_URL`, `SUPPORT_URL` | 実在し公開済みのURLだけ。外部媒体から公式サイトへは製品ページにdeep-linkし、実ストア内で完結する行動は直接そのストアへ。UTMは既存規則に沿う。 |
| `RELEASED_AT`, `PRICE`, `PLATFORMS` | 実際の公開日時、販売条件、対応OS/環境。デモ/学びでは該当しない項目を空欄にし、販売前情報を確定のように書かない。 |
| `MEDIA` | 素材ごとに`kind`, `path`, `purpose`, `alt_or_caption`, `rights_source`, `approved`を記録。素材がない/不要なら省略。実ファイルの場所は相対パスまたは `/assets/...`。 |
| `PUBLISH_ALLOWED`, `CHANNEL_STATUS` | 既存定義を維持。全素材・原稿の事実、権利、公開時期を人が承認するフラグ。媒体別に`skip` / `draft` / `approved` / `published`を記録する。 |

投稿素材ごとに同じ「変更」や「価値」を再入力しない。共通入力から草稿を作り、媒体ごとに焦点を変える。`PUBLISH_ALLOWED=false`なら外部公開用の完成原稿として扱わず、実投稿は承認者が媒体画面で最終確認する。

## X:入力から投稿を組み立てる

共通ルールは1投稿1メッセージ。冒頭で製品/変更/結果のどれが新しいか伝え、実画面や再現可能な結果を使う。抽象的なAI自慢、根拠のない性能比較、曖昧な「近日公開」、ハッシュタグの連続、意味のないURL貼付けは避ける。リンクが必要な場合だけ関連する製品ページ、note記事、実ストアへ送る。製品の外部告知では既存のUTM規則を使い、URL文字数を見てから投稿する。

| 用途 | 主に読む入力 | 出力の組み立て |
| --- | --- | --- |
| 製品リリース | `PRODUCT_NAME`, `TARGET_USER`, `ONE_LINE_VALUE`, `KEY_ACTION`, `PRICE`, `PLATFORMS`, `PRODUCT_URL`, `MEDIA` | 何ができる製品か → 誰のどんな場面に向くか → 公開状態/価格/対応環境 → 製品ページ。価格/環境は省略で判断材料を失う場合は投稿前に確認。 |
| 大型更新 | `VERSION`, `CHANGE_SUMMARY`, `USER_BENEFIT`, `EVIDENCE`, `PRODUCT_URL`, `MEDIA` | 変わった点 → 利用者への効果 → 画面/結果 → 更新済みページ。 |
| 小型更新 | `CHANGE_SUMMARY`, `USER_BENEFIT`, `PRODUCT_URL` | 価値が一文で伝わる変更だけを短く告知。内部整理だけなら投稿しない。 |
| 短いデモ | `KEY_ACTION`, `VISIBLE_RESULT`（`EVIDENCE`から選択）, `MEDIA`, `PRODUCT_URL` | 動画/画像の直前または本文冒頭で、見るべき操作と結果を示す。1クリップに複数機能を詰めない。 |
| 技術的な学び | `PROBLEM`, `METHOD`, `EVIDENCE`, `LIMITATIONS`, 必要なら`ARTICLE_URL` | 課題 → 試したこと/結果 → 限界。一般論で終わらせず、詳細記事がなければ無理にリンクしない。 |
| 不具合修正 | `VERSION`, `CHANGE_SUMMARY`, `USER_BENEFIT`, `RELEASED_AT`, `SUPPORT_URL` | 誰に何が起きていたか → 修正されたこと/適用方法 → 必要ならサポート情報。情報漏えい等の調査中案件は公開前に人が判断。 |
| note記事告知 | `ARTICLE_TITLE`, `READER_PROBLEM`, `ONE_FINDING`, `ARTICLE_URL`, 任意の`PRODUCT_URL` | 記事で得られる具体的な知見 → 記事リンク。本文をそのまま転記せず、製品リンクは記事と直接関係するときだけ。 |

## note: 読者のための記事を先に作る

記事化する価値がある場合だけ、次の順で構成する。

1. 読者の課題・疑問
2. 前提、利用環境、制約
3. 試したこと
4. 採用した判断と理由
5. 実装または検証方法
6. 実際の結果、失敗、限界
7. 読者が持ち帰れる知識・手順
8. 関連製品の情報とCTA（関係がある場合のみ）

一つの製品紹介だけで終わる記事にはしない。製品仕様の正本は公式製品ページ、背景や検証の読み物はnote。公開前に製品URLがない場合はリンクを捏造せず、販売予定日を約束しない。告知文は`ARTICLE_TITLE`, `READER_PROBLEM`, `ONE_FINDING`, `ARTICLE_URL`から別途作る。

## OG画像: 共有時に製品を識別できる一枚

- サイズは1200×630 PNG。現在の`node scripts/check-release.mjs`は公開ページのOG画像について実在PNG、1200×630、5 MiB以下を検査する。
- 基本レイアウトは、背景 → 正本ロゴを原形のまま合成 → 製品名 → 短い価値説明 → 必要な場合だけ実画面。
- 正本ロゴはA.I. TERMINALリポジトリの`assets/brand/assistant-a/master-original.jpg`。そのリポジトリには触れない。正本をそのまま使い、形状・縦横比を変えず、描き直し/生成AIによる再生成/文字や輪郭の改変/製品画面との一体化をしない。拡大縮小が必要なら縦横比を維持する。
- 助手Aの共通ブランドOGである既存`assets/og-home.png`はホーム用として維持する。製品のOGでは製品名と実画面等を使い分け、共有カードを見ただけでもどの製品か判別できるようにする。共通背景色や余白感は継承してよいが、ロゴ/製品を同じテンプレートに押し込み文字を小さくしない。
- 文字は製品名と一言価値を中心にし、説明文・価格表・機能一覧・CTAを詰めない。スマホ相当の小さなプレビューで製品名と要点が判読できることを人が確認する。SNSによるトリミング差があるため、重要要素を端に置かない。
- 製品画面を加えるのは実物が視覚的に意味を持つ場合だけ。キャプチャを歪めたり、実際にない操作/表示/評価/価格を載せたりしない。ロゴが製品UIの一部であるかのように見せない。

## スクリーンショット: 各画面の説明責任

枚数を先に決めず、購入/利用判断に必要な疑問へ答える画面を選ぶ。代表例:

| 画像 | 答える疑問 |
| --- | --- |
| メイン画面/ゲームの実プレイ | 実際に開くと何が見えるか、どんな雰囲気か |
| 主要機能 | どの操作で主要な価値を得るか |
| 利用結果/出力 | 操作後に何が得られるか |
| 設定/対応環境 | 必要な選択や環境上の制約があるか |
| Before / After | 具体的に何が改善したか。比較条件が同じか |

ソフトウェアは操作と結果が追える順に、ゲームは実プレイ画面を中心にする。スクリーンショットは実ビルド/実機から取得し、個人情報・アカウント名・トークン・ライセンスキー等をマスクする。マスキングを含む場合は機密だけを隠し、機能状態や実際のレイアウトを偽らない。端末枠などのモックアップ、合成UI、偽の通知/データは避ける。各画像に何を示すか分かるalt/captionを付け、altは「スクリーンショット」ではなく画面上で重要な内容を述べる。

## 短尺動画: 一つの動き、一つの結果

- 基準は5〜15秒、冒頭1〜2秒で操作/場面が始まり、イントロやロゴ演出で時間を使わない。
- 音がなくても内容が分かるよう、短い字幕または投稿本文で操作・結果を説明する。字幕はUIや重要部分を隠さない。
- ソフトウェアは入力/操作→結果が連続して分かる1機能を撮る。ゲームは実プレイの1場面や操作の手応えが分かる短い区間を選び、カットでゲーム速度・難度・成功率を誤解させない。
- 実UI/実プレイを用い、速度を変えた場合は視聴者の理解を損なわないよう表示する。カーソル移動や待ち時間を切る編集はよいが、性能測定のように見える内容は実測条件と数値の根拠を別に確認する。
- X、note、itch.io、公式ページすべてへ同じ動画を載せる必要はない。ページ用動画は読み込みと操作性を確認し、`preload="none"`等既存テンプレートの挙動を保つ。

## 1つの成果から必要な素材へ

1. 変更内容、利用者価値、根拠、制限を一つの更新レコードに記録する。公開可否を人が確認する。
2. 製品ページの事実とCTAを更新し、必要な実スクリーンショット/動画を決める。ページ更新自体が不要な軽微修正ならここで止めてよい。
3. 製品を共有カードから識別させたい場合に限り、専用OG画像を用意する。既存ホームOGを上書きしない。
4. 成果が一文で伝わるならX短文、画面の差が伝わるなら画像付き、動作が本質なら短尺動画を選ぶ。全部を同時に作らない。
5. 背景・判断・検証結果に読み物としての価値がある場合だけnote記事を作り、独立した記事告知を作る。
6. 実ゲームがitch.ioに公開されている場合だけストア説明/更新文を調整する。そこで購入/DLが完結するCTAを優先する。
7. 素材の権利、事実、alt/字幕、URL/UTM、公開時期を人が確認し、使わない媒体は`skip`と記録する。

## 素材ディレクトリとジェネレーターの接続

実製品公開時の案:

```text
assets/products/<slug>/
  og.png
  screenshots/
    screenshot-01.png
    screenshot-02.png
  videos/
    demo-01.mp4
```

画像は製品JSONの`ogImage`と`screenshot.src`から`/assets/products/<slug>/...`として参照する。動画は任意の`video.src`を同じ場所の`.mp4`パスへ向け、必要なら`video.poster`でポスター画像を指定する。現行generatorは製品ページで使うOG画像とスクリーンショットが`/assets/`内に存在することを要求し、OGはPNG、スクリーンショットはalt/caption/寸法を要する。videoはMP4 URLとローカル配布ファイルを検証する。SNS用の派生クロップや字幕付き動画は`MEDIA`レコードに登録し、製品ページ用の元スクリーンショットと混同しない。

今回このディレクトリや製品データを作らない。製品slugが確定する前に空ディレクトリやサンプル画像をコミットしない。権利/承認記録を残す場合は更新レコード等で管理し、非公開にすべき情報を静的サイトから配信される素材フォルダへ置かない。

## 自動生成・チェックと人の確認

将来、自動化しやすいものは、媒体別草稿/見出し/CTA/字幕案、投稿文字量の確認、素材ファイル存在、OG形式・サイズ、alt/caption欄の空欄、公開URL/UTM形式、placeholder文字列、承認状態の不足である。原稿生成の入力は既存更新レコードを使い、別CMSを作らない。

現在の責務は次の通り。

- `build-products.mjs`: 製品データから正式製品ページ、トップカード、sitemapを生成する。
- `check-release.mjs`: 公開ページのOG実体/寸法/容量、OG/Xメタデータ、実画面とalt、リンク、placeholder等を検査する。販促原稿の品質や素材権利は判定しない。
- 人: スクリーンショット/動画が実際の製品を正しく表すか、ロゴ正本との同一性、権利/個人情報、読みやすさ、字幕、誇張、公開時期、投稿可否と最終投稿を確認する。

必要性が出たら、販促素材のmanifestや媒体向けファイルを検査する軽量スクリプトを別責務で検討する。現時点では実製品・素材がなく、既存release checkerと重ねる価値もないため追加しない。機械検査を通過しても画像の真実性や権利を承認したことにはならない。

## 公開前の短いチェック

- [ ] 製品名、更新内容、価値、価格、対応環境、公開状態は製品ページと一致している。
- [ ] 画面/動画は実製品から取得し、権利・個人情報・秘密情報を確認した。
- [ ] OGは対象製品を判別でき、正本ロゴを原形のまま使い、スマホ相当の縮小でも読める。
- [ ] 画像alt/captionと動画の説明/字幕が内容に合い、視覚や音声だけに依存していない。
- [ ] 実際の公開URL/ストアURLだけを使い、媒体ごとのUTMを確認した。未公開リンクやplaceholderはない。
- [ ] 該当する媒体だけ選び、人が原稿・素材・公開時期を承認した。

最後に製品ページの公開物を`node scripts/check-release.mjs`で確認し、素材の見た目と実際の製品/ストア動作はプレビューで人が確認する。
